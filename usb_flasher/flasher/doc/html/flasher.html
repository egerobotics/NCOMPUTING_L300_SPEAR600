Chapter 3. Overview

USB boot, on SPEAr platforms, provides the means to flash the binary images to the NOR/NAND flash using USB device port. This technique is introduced to avoid the need of any external H/W tool other than USB Host PC to bring up the board.

To use this feature, SPEAr Board needs to be booted in USB Boot Mode. The USB flashing utility is used on the USB host side to carry out flashing. Current version of this utility is available for Windows and Linux host machine.

The flashing utility is flexible enough to support other features beside flashing with some changes. These possible features have been described in Appendix. In general it supports following key features.

3.1. Key Features

USB Flashing utility supports following features.

  • Ability to define partition layout for different memory (Nand/Nor) chips with different sector/block size
  • Save partition layout information in a file for later use
  • Ability to flash images to any of the configured partition
  • Support flashing jffs2 images for NAND
  • Save configurations that define images to be flashed to partitions
  • Receiving a binary file over USBTTY interface onto SPEAr board.
  • Run U-Boot commands and receive response
  • Update environment variables of u-boot

3.2. Features in v-2.4

This is a minor release with few bug fixes for default partition layout and firmware binaries updated against latest source.

3.3. Features in v-2.3

Release V-2.3 has following additional features.

  • support for SPEAr1310 RevC board
  • Existing SPEAr1310 has been renamed as SPEAr1310_revA and SPEAr1310_revC is referred as SPEAr1310 everywhere.

3.4. Features in v-2.2

Release V-2.2 has following additional features.

  • asciidoc based documentation support
  • Updated firmware (u-boot) binary for SPEAr1340 device
  • several small fixes

3.5. Features in v-2.1

Release V-2.1 has following additional features.

  • Faster file transfer due to enhanced Kermit implementation
  • Support for SPEAr1340 device
  • Support for Windows 7 64 bit, please refer installation on Windows 7
  • Command Interface to automate the flashing procedure
  • saveenv command (U-Boot Command for USBTTY mode) to save environment either in flash (nor) or in nand memory

This section covers installation and configuration required at SPEAr and Host PC level in order to use Flashing tool. This step is mandatory before start using Flashing utility.

4.1. Components Required

Following components are necessary to be installed on Host Windows PC to use the Flashing utility.

  • TCL-TK version 8.5
  • libusb-0.1
  • usbserial driver

These are the pre-requisite for flashing utility. For windows, the libusb driver and usbserial driver are already present with the tool. TCL-TK has to be downloaded and installed from the following path http://www.activestate.com/activetcl/

The Flashing tool uses TCL/TK to present the GUI interface for flashing. The libusb and usbserial drivers are used in different stages to provide the communication medium with the SPEAr board. This would be described in later sections.

4.3. Compilation of usb_send and ukermit

usb_send is used to connect the board with host PC and ukermit is used to load the binary file. Their compiled binaries are already included in Tools/Windows/.

User can make changes in usb_send and ukermit utilities to suit there needs. To recompile the binaries following components are required.

  • gcc compiler
  • libusb development library which is already present in Tools/src/usb_send/lib/Win/

To compile the usb_send,

Go to directory: flasher/Tools/src/usbsend/

# make WINDOWS=1

Move usbsend.exe to directory: flasher/Tools/Win/

To compile the ukermit,

Go to directory: flasher/Tools/src/ukermit/

# make WINDOWS=1

Move ukermit.exe to directory: flasher/Tools/Win/

flasher/Tools/Win/ is the default location from where flasher picks up the usb_send and ukermit tools binaries.

5.4. Run Flashing utility as non root user

Flashing utility have to access USB bus in order to communicate with SPEAr boards.

By default, in a Linux system only user "root" has the required privileges to access to system devices. Using "root" in the host PC for common tasks like upgrading board firmware is highly discouraged, since any command wrongly typed can lead to undesired changes in system configuration and, in worst case, determine system instability.

This chapter explains how to use the Linux system tool "udev" for configuring a Linux system to dynamically assign the proper permission to the USB devices associated to SPEAr. This is enough to allows unprivileged users (non "root") to use Flashing utility.

Flashing utility needs to use two classes of USB devices:

  • SPEAr boot ROM USB device
  • USB serial emulation device

The unprivileged user intended to run Flashing utility have to be allowed to access to both classes.

To enable access to SPEAr boot ROM USB device, Flashing utility provides an "udev" rules script in folder "contrib". The script have to be copied in the "udev" configuration folder, then "udev" have to be instructed to reload the configuration. As "root", type:

# cp contrib/udev.rules /etc/udev/rules.d/95-spear.rules
# udevadm control --reload-rules

Such script assigns to group "plugdev" the USB device of SPEAr. In order to use Flashing utility, user have to be part of the group "plugdev".

First of all, group "plugdev" must be created if not already present. Type

# getent group | grep ^plugdev:
plugdev:x:501:user1

to determine if the group is already present. Expected output would be similar to the text reported above. In case of no output, the group does not exist and have to be created with command

# groupadd plugdev

Then, unprivileged user have to be added to group "plugdev". As example, user "stm" is added to "plugdev" with following command.

# usermod -a -G plugdev stm

To verify that user "stm" is correctly added to the group, type

# id stm
uid=500(stm) gid=500(stm) groups=500(stm),501(plugdev)

The output reports all the groups the user belongs. "plugdev" must be in the list, as in the example.

At last, user access have to be granted also for USB serial emulation devices. "udev" rules for this purpose are normally part of Linux distribution. In Fedora Linux, every serial device is assigned to group "dialout". You can check permission of default serial port

# ls -l /dev/ttyS*
crw-rw----. 1 root dialout 4, 64 May 17 13:48 /dev/ttyS0

By adding unprivileged user to group "dialout" (in Fedora), the user would be able to access to every USB serial emulation device. In the example below it’s used again user "stm"

# usermod -a -G dialout stm

The modification to user group would be effective after next login of the user. If you are logged in as unprivileged user and then switched to "root" to type the commands above, then logout and login again to activate the modifications. No need to reboot your Linux box.

By allowing unpriviledged user to access to serial devices, the user will be also able to run serial communication programs, e.g. "minicom", without need for "root" privileges.

Chapter 7. Command Interface Usage

Command Interface can be used to upgrade and erase the flashes (NOR/ NAND) on board. It can also used for automating the flashing procedure. Command Interface is supported on the Windows (DOS) as well as on Linux Host Machine.

Command Interface (flasher.tcl) can be invoked in the following modes:

  • Interactive Mode 

    # tclsh flasher.tcl -i

  • Script/File Mode (flasher 

    # tclsh flasher.tcl -f script.txt

  • GUI Mode 

    # tclsh flasher.tcl
or
# wish flasher-gui.tcl

Install cmdline package before using the command interface. With Activetcl, it is already installed on Windows machine. Install with yum or apt-get on linux platform

Ensure that the executable is installed with a name tclsh eg. the binary name is tclsh85 for tcl-8.5 installation. In such case, create a soft link with the link name as tclsh.

7.1. Interactive Mode

Interactive mode provides following set of basic command for the flashing procedure:

  • [c]onnect : connects with the SPEAr device
  • [s]end : to load file to the SPEAr device
  • [f]lash : to flash the nand/nor memory
  • [u]cmd : runs the basic U-boot command
  • c[o]nfig : config reads the configuration file
  • e[x]it: exits the interactive mode
  • [h]elp: prints help for interactive mode
  • sa[v]eenv: save environment variable in either nand or nor memory

Apart from this commands , user can run U-boot commands directly on the console.So if the interface founds any such command which is not from the above list, it runs the command on the U-Boot.

7.1.1. connect command

connect command runs the connect.tcl script. It sends the initial binaries for ddr driver and customized u-boot.

connect command takes argument for the device to be connected.

Short and Long argument option for the device can be -d and --device respectively.

# flasher -i
flasher> connect --device SPEAr900
or
flasher> c -d 900

Following SPEAr SOC devices can be connected:

  • SPEAr300
  • SPEAr310
  • SPEAr320
  • SPEAr600
  • SPEAr900
  • SPEAr1300
  • SPEAr1310_reva
  • SPEAr1310
  • SPEAr1340

Argument can be SPEArxxx or xxx, in case of xxx argument it concatenates the string "SPEAr" with xxx.Here xxx can be 300/310/320/600/900/1300/1310_reva/1310/1340

Figure 7.1. connect command


7.1.2. send command

Once the device is connected, it gives the u-boot environment which is used to perform further flashing procedure.

send command is used to load the image file in the memory.send command runs the send.tcl script which in turn invokes the ucmd.tcl script for u-boot command and ukermit binary for file transfer.It ensures the valid file path.

It does following tasks in order:

  • runs loadb command on the u-boot (loadb: load binary file over serial line (kermit mode) )
  • executes the ukermit binary, which transmits the image file
  • runs imi command on the u-boot (imi: prints the image information loaded in the memory)

send command load the image file at the address 0x800000 by default.It takes the single argument for the file path. Argument for port and the load address is optional.

flasher> send --file ../lsp/spear300_xlaoder.img
or
flasher> s -f ./lsp/spear3xx_uImage.img -a 0x130000 -p COM5

Figure 7.2. send command


7.1.3. flash command

flash command is used to flash the images at any address in the nor and nand memory. It is based on the script flash.tcl which in turn depend on the send.tcl script for loading the image into the memory and ucmd.tcl script to run the u-boot command.

It does following task in order:

  • load the image in the memory at address 0x800000
  • calculate the filesize and align it with the sector size of the nand or nor memory
  • erase the nor or nand memory from the base address till the aligned size of file
  • copy the image file from the memory to the nand or nor memory

The sector size for Nor memory is assumed to be 0x10000. The sector size for nand memory will be found by running nand info command.

flash command takes following three argument:

  • -f / --file : file path to be flashed
  • -a / --address : base address of nor or nand memory at which image will be flashed
  • -m / --memory : nor / nand memory

Argument for the port is optional.

flasher> flash --file ../lsp/spear300_xlaoder.img --address 0xe6000000 --memory nor
or
flasher> f -f ./lsp/spear3xx_uImage.img -a 0xe6000000 -p COM5 -m nor

Figure 7.3. flash command


7.1.4. ucmd command

ucmd command is used to run the U-Boot command.It is uses the ucmd.tcl script.

It takes the command to be run as argument. Argument for the port and the expect string is optional. In default case port is found by listing all the COM (on Windows) or /dev/ttyACM (on Linux) ports on host machine and selects last port created from the list. Expect string or end by default is "u-boot>".

U-Boot commands can be run direcly on the console.Hence following two example commands produces same result.

flasher> ucmd -c print
or
flasher> print

Figure 7.4. ucmd command


7.1.5. config command

config command is used to read the configuration file of the device. It takes the SPEAr SOC device as argument.

flasher> config SPEAr900

Figure 7.5. config command


7.1.6. exit command

It exits the interactive mode of the flasher.

7.1.7. help command

It prints the help for the interactive mode.

Figure 7.6. help command


7.1.8. saveenv command

It is used to save the environment variables into either nand or nor memory.

saveenv command takes following two argument:

  • flash(nor)/nand memory

  • address at which environment variables are stored 

    flasher> saveenv flash 0xe6040000

7.2. Script Mode

Set of commands used in the interactive mode can be saved in text file. Flasher in script mode can be invoked on the command line which runs all the commands saved in previously stored in the text file.

One such example of script (text file) is shown below. First line in text connects with the device. Next three commands will flash the Xloader, u-Boot and Linux image in the nor memory at different addresses. Fifth command is not from the set of command of interface, hence it runs direcly on the U-Boot.

Example 7.1. Example of Script (text file)

1 connect --device SPEAr900
2 flash --file ../../lsp/spear13xx_uImage.img --address 0xe6050000 --memory nor
3 flash --file ../../lsp/spear900_xloader.img --address 0xe6000000 --memory nor
4 flash --file ../../lsp/spear900_u-boot.img --address 0xe6010000 --memory nor
5 version

Script mode can be used to automate the flashing procedure.

Chapter 9. Flashing Utility Architecture

Flashing Utility Architecture uses different components at different stages to accomplish flashing operation.

In the very first stage the USB boot mode support available in SPEAr platform BootROM is used. In this mode the BootROM enumerate itself as a generic USB device capable of receiving and executing any binary transferred by USB host.

As soon as a binary/firmware is transferred from USB host, BootROM executes it and then the control can be taken over by the firmware itself to present any desired interface or to perform any task.

In the USB flashing utility this firmware is a DDR driver (xloader) and customized u-boot to enumerate SPEAr device as a serial device (tty over USB) which can then be used from host to send any u-boot command.

This interace is then used to execute u-boot commands to perform flashing operation. The Host side flashing GUI hides this complexity by offering a simple user interface for flashing operations.

9.1. BootROM (USB boot)

Refer BootROM manual of the respective SPEAr device.

9.2. Flashing Utility Firmware (Xloader and U-Boot)

As mentioned before, following are the steps involved in setting up the flashing interface on usb host.

  • Configure boot-strap for usb boot and power-on SPEAr
  • Connect USB host which would see a vendor specific usb device
  • SPEAr bootrom which exposes this interface receives Xloader from usb host and execute it to initialize DDR
  • After Xloader, u-boot is sent which is again executed by BootROM
  • u-boot takes over usb interface re-enumerating as usb-tty interface

These steps leave U-Boot running on the SPEAr device. Now, U-Boot commands can be run on a serial interface exposed to the Host machine to support erasing and flashing of NAND and Serial NOR device. The U-boot source code is same available with SPEAr LSP. This special U-Boot boot loader is build to support TTY over USB.

To generate this firmware image, U-boot build has to be done in the following way:

$ make spearXXX_usbtty_config

Similarly, DDR2 driver image can be generated from Xloader source using the following command:

$ make spearXXX_usbtty_config

9.3. tty over USB

The USB serial device driver provides serial port emulation on Windows operating systems by implementing a serial link emulation protocol on USB. The driver exposes a Win32-compatible COM port and in addition provides some unique features such as a Plug-Play compliant device instance enumeration method. This avoids confusion about COM port numbers and improves usability. The CDC ACM driver on Windows exposes the USB device as a virtual COM port to the operation system

The USB serial driver enables sending both data and command either through ACM or through serial emulation.

tty over USB Features:

  1. Exposes a virtual COM port that is compatible with the Win32 serial port
  2. COM port can be used by standard Windows programs such as HyperTerminal
  3. COM port name gets assigned automatically
  4. Supports add and remove notifications and a Plug & Play compliant port enumeration and identification method that is not based on COM port names
  5. Optional static COM port behavior to support legacy applications. The application can keep the COM port opened while the device is removed and continue the communication if the device is reconnected.

9.4. tty over USB Usage in Flashing Utilities

The exposed TTY interface (TTY over USB) can be used on the Host side as a U-Boot console to send commands and receive response. This enables to run all the U-Boot commands over the USBTTY link. Also, the same link is used to download Binary Images at virtually the USB speed through standard Kermit protocol.

For example, erasing a partition in Serial NOR chip can be easily done by sending the command

erase 1:5-10
